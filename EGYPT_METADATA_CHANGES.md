## 1. Program rule `EyEQgk3QCHX` — "Risk Override if Age not eligible"

| | |
|---|---|
| **Object** | Program rule, `EyEQgk3QCHX`, priority 3 |
| **Field changed** | `condition` |
| **Changed by** | manu |
| **Changed on** | 2026-09-15 08:05:33 UTC (server `lastUpdated`) |
| **Status** | Applied on sandbox — **to transmit to Egypt** |
| **Other rules touched** | None. `q8BMOuJd4w9` and `IG8uBGYVptG` deliberately left unchanged. |

### Before

```
d2:hasValue(A{age}) && (A{age} < 40 || A{age} > 75)
```

### After

```
d2:hasValue(A{age}) && (A{age} < 40 || (A{age} > 75 && !(A{historyHeartAttack} == true || A{historyStroke} == true || A{historyKidneyDisease} == true) && (d2:hasValue(#{cholesterol}) || A{Patient_Diabetes} != 'YES')))
```

Validated with `POST /api/programRules/condition/description?programId=pMIglSEqPGS`
→ `status=OK, message=Valid`.

### Why

Three program rules assign to the same data element,
`DKKPQKIO9qN` (HTN - Risk - Clinical Override):

| Priority | Rule | Condition | Assigns |
|---|---|---|---|
| 1 | `q8BMOuJd4w9` | `age >= 40` && no cholesterol && diabetes && no history | `'DIABETES'` |
| 2 | `IG8uBGYVptG` | `age >= 40` && any CVD history | `'HISTORY_CVD'` |
| 3 | `EyEQgk3QCHX` | `age < 40 \|\| age > 75` | `'AGE_NOT_ELIGIBLE'` |

Rules 1 and 2 have no upper age bound, so a patient **over 75** satisfies both
`age >= 40` and `age > 75`. Rule 1 or 2 writes a value, then rule 3 tries to
overwrite it and the import is rejected:

```
[E1307] EVENT QvC06aBcJ2g: Generated by ProgramRule (`EyEQgk3QCHX`) - Unable to
assign value to DataElement `DKKPQKIO9qN`. The provided value must be empty or
match the calculated value `AGE_NOT_ELIGIBLE`
```

Reproduced on patient `LZEMaFsa95q` — age 84, diabetes YES, no cholesterol, no
CVD history — which matches rule 1 and rule 3 simultaneously.

The fix narrows rule 3 rather than rules 1 and 2, because a patient over 75 with
CVD history or diabetes must still be flagged as high risk; only the *fallback*
"no score available" case should yield `AGE_NOT_ELIGIBLE`. The WHO CVD risk
charts for North Africa and the Middle East cover ages 40-75 only, so over-75
genuinely is not scoreable — but an override that reflects real risk takes
precedence over the absence of a score.

### Resulting behaviour

Exactly one rule now writes in every scenario:

| Age | CVD history | Diabetes & no cholesterol | Override assigned |
|---|---|---|---|
| < 40 | any | any | `AGE_NOT_ELIGIBLE` (rule 3) |
| 40-75 | yes | — | `HISTORY_CVD` (rule 2) |
| 40-75 | no | yes | `DIABETES` (rule 1) |
| 40-75 | no | no | none — numeric score used |
| > 75 | yes | — | `HISTORY_CVD` (rule 2) |
| > 75 | no | yes | `DIABETES` (rule 1) |
| > 75 | no | no | `AGE_NOT_ELIGIBLE` (rule 3) |

The three conditions are now mutually exclusive, so the priority 1/2/3 ordering
is no longer load-bearing.

### Notes for the Egypt team

- Rule 3's outcome is evaluated per event, because `d2:hasValue(#{cholesterol})`
  is event-level. This matches how rule 1 already behaved.
- An empty diabetes attribute satisfies `A{Patient_Diabetes} != 'YES'`, so
  patients with no recorded diabetes status fall through to rule 3 as intended.
- Worth auditing the `HTN - Risk = N` numeric score rules for the same pattern:
  any that gate on `age >= 40` without an upper bound can collide with each
  other or write a score for a patient over 75.

## 2. Program rules — BMI 35 boundary in the CVD-risk chart

| | |
|---|---|
| **Object** | 45 program rules, the `HTN - Risk = N` chart cells |
| **Field changed** | `condition` — 140 occurrences across the 45 rules |
| **Changed by** | manu (via `fix_bmi35_boundary.py`) |
| **Changed on** | 2026-09-16 10:52 local |
| **Status** | Applied on sandbox — **to transmit to Egypt** |
| **Backup** | Original conditions in `bmi35-backup-20260916-105111.json` |

### Before

The 30-35 obesity band and the band above it were both closed at 35:

```
... && #{bmi} >= 30 && #{bmi} <= 35      (the 30-35 cell)
... && #{bmi} >= 35                       (the 35+ cell)
```

### After

```
... && #{bmi} >= 30 && #{bmi} < 35
```

Each new condition was validated with
`POST /api/programRules/condition/description?programId=pMIglSEqPGS`
→ `status=OK, message=Valid` before being saved.

### Why

A BMI of exactly 35.0 satisfied both cells, so two rules fired and each
assigned a different value to `qwCWN0aLHAi` (Risk Score) and `m5WImperUYv`
(Risk Final Classification). Worked example — male, smoker, age 40, systolic
110, BMI 35.0, no cholesterol on file:

```
'HTN - Risk = 8'   cell BMI >= 30 and BMI <= 35   -> score 8,  MODERATE
'HTN - Risk = 10'  cell BMI >= 35                 -> score 10, HIGH
```

At systolic 180 the same patient drew `VERY_HIGH` from one rule and `CRITICAL`
from the other, so the disagreement spans a whole risk band rather than a
point or two.

Consequences:

* **On import** DHIS2 refuses two different assignments to one data element and
  rejects the entire tracked entity with `E1307`. 27 of 1000 generated patients
  (2.7%) were lost this way.
* **In the capture app** there is no import to reject, so one rule simply wins
  by evaluation order. The patient silently receives either classification,
  with nothing flagged. Since the statin nudge triggers above 10% risk, score 8
  versus 10 can also change whether a statin is suggested.

BMI is computed by rule `BMI_Calculated` and rounded to one decimal, so 35.0 is
an ordinary value — a patient of 90 kg at 160.4 cm produces it.

### How it was found

The `E1307` message names the calculated value but not the competing rule, so
the rules were checked directly: all 69 conditions that assign `qwCWN0aLHAi`
were transpiled to Python and evaluated over a grid sitting on and around every
boundary in the chart (17 ages, 13 systolic values, 15 BMI values, 14
cholesterol values, both sexes, smoker and non-smoker, three diabetes states) —
50,388 combinations per data element.

### Verification

| | Before | After |
|---|---|---|
| Risk score, conflicting grid points | 662 | **0** |
| Risk classification, conflicting grid points | 60 | **0** |
| Grid points matching no rule (age 40-74) | 0 | **0** |

Every conflict found was at `bmi == 35`; no other BMI, age, systolic or
cholesterol boundary was affected, and the chart has no gaps. The remaining
boundaries are all half-open (`>= 20 && < 25`) and were already correct.

### Not covered by the grid

Five rules could not be evaluated automatically and were read by hand:

* `Reset Risk Score to null if missing data for calculation` — assigns `null` /
  `'UNKNOWN'` when inputs are missing, so mutually exclusive with any chart cell.
* `Risk Score unavailable - clear and hide field` — its condition begins
  `false && (...)`, so it can never fire.
* `WARNING Risk based on patient being diabetic and over 40` and
  `WARNING Risk based on patient having a history of CVD` — assign `'HIGH'` and
  `'VERY_HIGH'` to `m5WImperUYv` when `#{clinicalOverride}` is set. These are a
  **second, independent conflict path**: they write the same data element as the
  chart cells, so a chart value of `MODERATE` plus an override of `HIGH` in one
  evaluation is the same `E1307` pattern. Not reachable from an import that
  leaves `DKKPQKIO9qN` empty, but reachable in the app. **Not investigated
  further — worth a look.**

### Before

The population estimate was a literal `100000` written into the indicator
expressions rather than held anywhere reusable. Two before-values were captured
from the server prior to the change:

```
iVPEm0eRK7a  HTN - Estimated adults with hypertension   numerator = 100000, denominator = 1
YjnObFwrKat  DM - % of people with controlled blood sugar  denominator = 100000
```

The before-values of the other seven were not captured before they were edited,
but all nine were consistent with the same literal.

### Why

Two separate problems with one cause.

**Maintainability.** The same population figure was duplicated across nine
expressions, so changing it meant nine edits kept in step by hand. A constant
gives one place to change and makes the shared denominator explicit.

**The cascade was unreadable.** With a denominator of 100000 against a demo
cohort of ~1000 patients, every bar after the first rounded to well under 1%:

```
estimated adults with hypertension   100000   100%
registered                              741    0.74%
under care                              725    0.73%
BP <140/90                               389    0.39%
BP <130/80                               299    0.30%
```

With the constant at 1000 the same data renders as an actual cascade:

```
estimated adults with hypertension     1000   100.0%
registered                              741    74.1%
under care                              725    72.5%
BP <140/90                              389    38.9%
BP <130/80                              299    29.9%
```

and for diabetes: registered 53.3%, under care 52.0%, controlled blood sugar
14.6%.

### The constant has to be kept in step with the cohort size

This is the one thing to watch. The constant is a **population estimate**, so it
only produces a sensible cascade while it exceeds the number of registered
patients. At 75% hypertension prevalence in the generated cohort:

| `--patients` | HTN registered | as % of a 1000 estimate |
|---|---|---|
| 1000 | ~750 | 75% |
| 1500 | ~1125 | **112%** |
| 2000 | ~1500 | **150%** |
| 3000 | ~2250 | **225%** |

Above ~1300 patients the cascade bars exceed 100% and the chart becomes
nonsense. Rule of thumb for a registration rate of about three quarters:

```
n1e76QJKUzt  ~=  patients x 0.75 / 0.75  =  patients
AQwjmAAFrCh  ~=  patients x 0.55 / 0.55  =  patients
```

so setting both constants equal to `--patients` keeps the first cascade bar near
75% for HTN and 55% for DM. On a real instance the constants should instead come
from the actual catchment population and prevalence, and the demo values are
only a stand-in.

### A rejection worth remembering: E7619

The first ADEx run computed 20 values correctly and then had all 20 rejected:

```
E7619  Value must match value type of data element `iRgb6hOfzEk`:
       value_not_zero_or_positive_integer
```

Cause: the indicator had been built field by field and lacked `decimals`, which
every working indicator sets to `0`. Without it the computed value carries a
decimal part, which an `INTEGER_ZERO_OR_POSITIVE` data element refuses. It also
lacked `orgUnitField` and, initially, `analyticsPeriodBoundaries` — an
EVENT-type indicator with no boundaries produces malformed SQL
(`syntax error at or near "and"`).

**Create program indicators by cloning a working one**, then change only name,
filter and identifiers. The indicator built that way (5b) had all three fields
right from the start; the hand-built one needed three separate repairs.

### Two measurement traps

Both cost real debugging time and will mislead anyone repeating this work:

1. **A newly created program indicator's filter is ignored until the analytics
   tables are rebuilt.** Before the rebuild, the impossible filter
   `A{jCRIT4GMMOS} == 'NEVER'` still returned 169; afterwards it correctly
   returned 0. Sequence: create → run analytics → then measure.
2. **Analytics responses are cached.** Editing an indicator and re-querying
   returns the stale value — the same query returned 80, then 169 after
   `POST /api/maintenance?analyticsCacheClear=true`.

### Numbers as measured

```
period    under care   contactable overdue (5a)   verification (5b)
202607          701                         89                 160
202608          715                         86                 162
202609          715                         80                 162
```

Reference counts taken straight from tracker data for hypertensive, ACTIVE,
contactable patients:

```
overdue as at 2026-09-01 (period start): 129
overdue as at 2026-09-16 (today):        162
follow-up TEA says OVERDUE_PENDING_CALL: 162
```

5b agrees exactly with "overdue today", which is what it measures: the
follow-up status attribute holds **current** state, so 5b is a valid check for
the current period only — for a completed month it reports today's overdue set
rather than that month's.

5a measures the period start, where the reference is 129 against its 80. Part
of that gap is expected in this synthetic cohort, whose due dates cluster in
the last three weeks, but it has **not** been fully explained and is worth a
look on real data. 5a is the more trustworthy of the two by construction.

## Observations not yet changed

Recorded here because they affect the Egypt instance but no metadata has been
modified for them.

### Patient follow-up status must agree with the booked appointment

No metadata was changed for this; it is a constraint on anyone loading data.

`rgeuEnAI0nj` (HTN - Patient follow-up status) is a **derived** value, not an
independent one. The overdue indicators read it, so it has to agree with the
patient's own scheduled visit:

* due date already passed -> `OVERDUE_PENDING_CALL`
* due date still ahead    -> `UPCOMING_VISIT`

Two things were learned the hard way while generating demo data:

1. Setting it to an arbitrary value from the option set leaves roughly two
   thirds of patients contradicting their own appointment, and the overdue
   indicators then report nonsense that looks plausible.
2. Deriving the appointment mechanically as "last visit + 28 days" makes
   almost everyone overdue: a patient last seen 60 days ago is 32 days late by
   construction. Measured at 68% of the cohort before the appointment date was
   decoupled from the last visit date. A patient who is keeping up needs an
   appointment dated in the future.

The same applies to `fI1P3Mg1zOZ` (NCD Patient Status), which program rule
`GYmydeVoxDI` assigns as `ACTIVE` when an enrollment is created. A status of
DIED or TRANSFER therefore cannot be supplied in the creating payload; it has
to be a second update afterwards, at which point the rule does not re-assert
and the value sticks. Verified on the server, and note it does **not** require
`skipRuleEngine` - the earlier note in this file about E1309 applies to
creation only.

### CVD risk score DOES populate on server-side import — earlier note corrected

An earlier version of this file recorded that the risk score does not populate
on import and that the risk assessment is a capture-app plugin. **That was
wrong.** The score is produced by 69 ordinary server-side program rules and
does populate on import, provided two inputs are supplied explicitly:

* `ea5w3mkinZo` (Age for TEI header), normally assigned by rule from the date
  of birth, and
* `J2YWUFBEyvZ` (BMI), normally assigned by rule `BMI_Calculated` from height
  and weight.

The chart conditions test `A{age}` and `#{bmi}`, and during an import a rule's
own `ASSIGN` output is not visible to another rule's condition. Leaving both to
their rules starved the chart conditions and produced the 1-in-212 result that
was originally observed. Sending the same values those rules would compute
raised coverage to 7,391 of 8,038 completed visits (92%); the remainder are the
under-40 and over-75 patients the chart cannot score.

### Total cholesterol mmol/L is rule-derived

`pSqsIKFb8NX` (Total Cholesterol mmol/L) is assigned by rule `dRSNL8k6vk6` from
the mg/dL value `eNqHpd5y3zk`. Supplying it in an import payload fails with
E1307 unless the value matches the rule's own rounding exactly. Confirmed firing
on 105/105 visits that carried a mg/dL value.

### NCD Patient Status is rule-derived

`fI1P3Mg1zOZ` is assigned `ACTIVE` by rule `GYmydeVoxDI` for an open enrollment,
so a migrated status of INACTIVE / TRANSFER / DIED is rejected with E1309.

### Pilot org unit hierarchy is a single governorate

The hierarchy is `Egypt > Al Qalyubia > district > facility`, 20 facilities at
level 4. The district option set `zj1FfMoKhhC` contains 365 districts across all
governorates, so district values assigned without reference to the org unit
hierarchy will not match the facility's real geography.
